# MechJeb analysis and controller attribution

The existing opt-in flight callback attribution observer now includes `callbackAttribution.mechJebDrive`. It does not enable the provider replacement or change control behavior. The observer binds the installed MechJeb2 assembly SHA/MVID and the exact token/IL of Core.Drive, VesselState.Update and AnalyzeParts. Concrete controller Drive implementations are discovered only in that pinned assembly, bound to its original virtual dispatch, and rejected if another Harmony owner has modified the seam.

Admission captures active-vessel Core→readonly VesselState identities. No master lookup or Enabled getter is added to the hot path. The original master and enablement branches retain control of execution. Core.Drive records its original envelope; Update and AnalyzeParts record matching-owner inside-Drive and outside-Drive rows. The outside rows matter because Core.FixedUpdate can update the state before Drive and the existing UT cache can make Drive's later Update inexpensive. Controller rows group actual runtime type, require its readonly Core to match the currently executing Drive, and include nested calls of that type. No provider, controller or multicast subscriber is invoked twice.

Each row retains total and recursion-aware outermost counts/ticks, including unobserved zero rows. These are inclusive wall envelopes, not exclusive CPU. Different rows overlap. Per-call Harmony, reflection, counters, timers and nested observers perturb the workload; `observerOverheadStatus` remains unqualified. The preexisting timer floor measures only adjacent clock reads. Admission start/end timestamps charge binding and patch preparation separately. The observer covers its lifetime's fixed subtree rather than promising exact Probe-window alignment.

Inherited Drive reflection wrappers are resolved to the exact declared module/token implementation before patch deduplication. Controller rows retain the physical `declaringType`, module/token and `ilSha256`, with the executing controller class recorded separately as `runtimeType`. Positive calls demonstrate actual execution under the original enablement branch; zero-call admitted types do not establish that those controllers were enabled.

Native interpretation requires positive Core.Drive entry, observed owner IDs, zero observer errors, exact pinned identities and removed owned patches. The core-drive-entry-envelope includes calls rejected by the original master branch; positive entry alone does not establish master or controller execution. Check actual controller activity and inside/outside Update and AnalyzeParts counts before selecting an analysis or controller replacement. An installed mod without a Core on the active vessel reports not-present. Unsupported or foreign seams remain unavailable/invalid, with original game methods left in charge. Compilation and the focused console proof are not native admission.

The private 512-part upper-atmosphere capture admitted the canonicalized methods and completed with unchanged topology, zero observer errors and removed owned patches. Twenty physical methods represented 59 controller runtime types. One observed Core matched the six admitted owners. Across 153 calls, nested inclusive averages were Core.Drive 0.950ms, inside-Drive Update 0.899ms and AnalyzeParts 0.840ms. Outside-Drive Update had 153 tiny cache-hit envelopes and outside-Drive AnalyzeParts had no calls. Actual ThrustController execution averaged 0.0163ms; inherited no-op rows retained ComputerModule as the physical declaration and concrete runtime types separately.

This resolves the analysis-versus-controller question for that fixture. AnalyzeParts is the next MechJeb boundary to investigate: original ordered part/module/provider reads and live transforms followed by reductions. Its inner operations remain unranked, so no particular replacement gain is established. Do not sum its nested rows, infer controller enablement from zero rows or extrapolate the intrusive fixed-subtree lifetime to exclusive Probe-window CPU.

The broader capture still points beyond MechJeb: ScriptRunBehaviourUpdate averaged 10.24ms per observed frame and ScriptRunBehaviourFixedUpdate averaged 8.55ms per observed fixed iteration. The latter includes the 3.13ms FlightIntegrator envelope; native PhysicsFixedUpdate averaged 2.04ms per observed fixed iteration. Frame/fixed counts and nested phases differ. Update ownership remains unresolved and deserves attribution before narrowing the program around MechJeb.
