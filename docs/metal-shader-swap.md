# One-shader Metal swap experiment

The menu reconstruction path uses `graft-menu` with one exact original name per line, optionally followed by a tab and an explicit donor name. Distinct original objects with the same public shader name may require different donor contracts. The graft validates ordered property names, types and texture dimensions, then preserves the original complete property table, shader name, path ID and dependency edges. This includes properties inspected by managed loading code: adding an unused texture property can change `HasProperty` and make stock loading dereference an absent texture. A compiled shader alone is insufficient proof of compatibility.

`prepare-menu-cook` can consume recovered private property metadata for authored experimental recipes. Those recipes preserve the exposed interface while their lighting and effects remain approximations requiring image inspection. Matching vendor and recovered UI sources remain separate inputs. Reconstructed game assets and source stay outside Git.

KSP 1's macOS build runs Unity 2019.4.18f1. Its `UI/Default` shader in `unity_builtin_extra` has compiler platform `[15]` (OpenGL). A Unity 2019.4.18f1 macOS AssetBundle built with only Metal enabled has the same shader with platform `[14]`. `KspContinuum.ShaderGraft` can replace that one serialized shader while preserving the target asset's path ID. This is an experimental change to an isolated KSP copy, not a working Metal port.

Build the donor with the [matching Unity editor](https://unity.com/releases/editor/whats-new/2019.4.18f1). Copy selected sources from [Unity's matching built-in shader archive](https://download.unity3d.com/download_unity/3310a4d4f880/builtin_shaders-2019.4.18f1.zip) under `tools/metal-shader-donor/Assets/MetalShaders/`. Set `CONTINUUM_SHADER_BUNDLE_OUTPUT` to an empty output directory and run the editor in batch mode with `-projectPath tools/metal-shader-donor -buildTarget StandaloneOSX -executeMethod BuildShaderBundle.Build`. The editor must have a valid license. Unity's shader sources and the generated bundle are local inputs; neither is committed here.

Each build explicitly selects the `.shader` assets currently under `Assets/MetalShaders/`. Existing asset-bundle labels elsewhere in the project, including labels left by earlier selections, do not add shaders or bundles to this build. The build leaves importer labels unchanged.

`KspContinuum.ShaderGraft` uses [AssetsTools.NET 3.0.5 and its classdata TPK](https://github.com/nesrak1/AssetsTools.NET/releases). Use `inspect <classdata.tpk> <asset-or-bundle>` to check Unity versions and shader platforms. Use `graft-list <classdata.tpk> <target-assets> <donor-bundle> <new-output-assets> <names-file>` to graft one name per line into a separate asset file in a single write. The original `graft` command remains available for one name. The tool requires the same Unity version, exactly one matching shader per name in each input, OpenGL-only target platforms, and Metal donors. Copy the output only into an APFS copy of a closed KSP instance; keep the original copy intact.

On the M4 Max test machine, both the unpatched Metal-configured copy and the one-shader copy reached `MAINMENU` at 1920×1080. The patched run changed missing-Metal-shader messages from 195 to 194 and missing `_Stencil` warnings from 10 to 0 in `Player.log`. A later two-shader batch (`UI/Default` and `UI/Default Font`) preserved both target path IDs and reached `MAINMENU`. Its `KSP.log` had 122 missing-platform messages versus 127 in an earlier one-shader menu run; the counts are diagnostic, not a controlled rendering comparison. Its in-game 1920×1080 screenshot was still black. Replacing two additional KSP-specific UI shaders in `globalgamemanagers.assets` with renamed Unity UI shaders stalled during internal-space loading before a screenshot could be captured. That substitution was only a diagnostic and is not evidence of a compatible KSP shader implementation. The Unity 6 player transplant failed much earlier on incompatible serialized assets, so matching Unity 2019.4.18f1 is the useful boundary for this experiment.

## Fast matching-Unity harness

The donor project also builds a small standalone Unity 2019.4.18f1 Metal player. Set `CONTINUUM_HARNESS_OUTPUT` to a new `.app` path, then run the same editor with `-batchmode -nographics -quit -projectPath tools/metal-shader-donor -executeMethod BuildHarness.Build`. Run the built app with `CONTINUUM_SHADER_BUNDLE` pointing to the donor bundle, `CONTINUUM_HARNESS_REPORT` pointing to a new report path, and `-force-metal -screen-width 1280 -screen-height 720`. The app renders a generated image through Unity UI's default material and the donor `UI/Default` material, writes a PNG beside the report, checks four corresponding framebuffer pixel pairs across the image, and exits with failure when they do not match. Missing bundle input also produces a failure report and nonzero exit. No KSP install, assets, or plugin are needed for this check.

On the M4 Max, the resulting 54 MB player reported Unity 2019.4.18f1, Metal, `donor_supported=True`, `visual_match=True`, and produced a 1280×720 PNG showing both images. This validates the donor shader in a matching Unity player. It does not validate its graft into KSP's asset file, KSP's material bindings, or KSP's other shaders. A subsequent unpatched KSP Metal run remained on a black window and stalled during part loading, so no menu frame-time comparison was taken. Keep KSP integration checks separate from this fast shader check.

Apple's [Metal developer tools](https://developer.apple.com/metal/tools/) offer GPU capture and profiling once a useful Metal frame is rendering. The [Game Porting Toolkit](https://developer.apple.com/games/game-porting-toolkit) also evaluates Windows binaries and converts DXIL shaders, but those paths do not directly replace KSP's Unity-serialized OpenGL shader variants. The current Xcode 26.6 install did not expose `gpucapture`, `gpudebug`, or `metalperftrace` through `xcrun`; obtaining those command-line tools is a separate setup step.
